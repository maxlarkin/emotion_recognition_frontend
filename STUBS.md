# Заглушки запросов

Это копия фронтенда из `emotion_recognition/frontend` (коммит `6135d77`), которая работает без бэкенда. Все запросы к REST API и оба WebSocket обрабатывает заглушка в самом браузере. В сеть ничего не уходит.

Камера и микрофон на экране «Веб-камера» настоящие (`getUserMedia`). Кадры и звук передаются в заглушку и не покидают браузер.

## Запуск

```bash
npm ci
npm run dev      # http://localhost:5173, бэкенд не нужен
npm run build    # tsc --noEmit + vite build, результат в dist/
npm test         # vitest
docker build -t emotion-frontend . && docker run --rm -p 8080:80 emotion-frontend   # nginx без прокси
```

## Где лежат заглушки

| Файл | Что делает |
|---|---|
| `src/api/index.ts` | Единая точка доступа к данным. Все члены `api` и функции `fetchHealth`, `fetchSessions`, `deleteSession`, `exportUrl` берутся из `./stub`. |
| `src/api/stub/index.ts` | Бэкенд в памяти: все REST-вызовы и `/ws/streams`. |
| `src/api/stub/live.ts` | Поддельный сокет `/ws/live` (`openLiveSocket`). Его создаёт `src/live/run.ts` вместо `new WebSocket(...)`. |
| `src/api/stub/sim.ts` | Симуляция: лица на камерах, вероятности эмоций, правило событий из `stack.md` (порог, минимальная длительность, пауза между событиями). |
| `src/api/stub/data.ts` | Демо-данные: 8 камер на 3 площадках, 5 файлов, 2 прошлых сеанса веб-камеры, ответ `/api/health`. Адреса камер взяты из диапазона `192.0.2.0/24`, он зарезервирован для документации. |
| `src/api/stub/stub.test.ts` | Тесты заглушек. |

Настоящие клиенты сохранены без изменений: `src/api/real.ts` (REST) и `src/api/streamsSocket.ts` (`/ws/streams`). Их тесты тоже остались. В сборку эти файлы не попадают, потому что их никто не импортирует.

Состояние заглушки живёт до перезагрузки страницы. Задержка ответа около 150 мс. Ответы возвращаются копией (`structuredClone`), как будто они пришли по сети.

## REST

Формы ответов совпадают с `interfaces.md` и типами из `src/api/types.ts`. Тексты ошибок совпадают с текстами бэкенда.

| Метод и путь | Функция | Где вызывается | Что отвечает заглушка |
|---|---|---|---|
| `GET /api/health` | `fetchHealth` | `shell/context.tsx`: опрос раз в 5 с, индикатор в шапке, «Настройки › Система» | `status: "ok"`, `device: "cuda"`, все четыре модели `true`, `gpu_name` RTX 3050 Laptop. |
| `GET /api/sessions` | `fetchSessions` | `sessions/SessionsView.tsx` («История › Сеансы») | Сеансы веб-камеры (2 демо плюс созданные на экране «Веб-камера»), сеанс `rtsp` для каждой камеры, у которой есть сессия, и все файлы. Сортировка от новых к старым. |
| `DELETE /api/sessions/{id}` | `deleteSession` | «История › Сеансы» | Удаляет сеанс, его события и таймлайн. Для статусов `running`, `queued`, `processing` возвращает ошибку «Сессия ещё идёт». Для неизвестного id — «Сессия не найдена». |
| `GET /api/sessions/{id}/export?format=csv\|json` | `exportUrl`, `api.fileExportUrl` | ссылки CSV/JSON в «Сеансах», «Экспорт» в результате анализа файла | Ссылка `data:` (не `blob:`), освобождать её не нужно. Колонки взяты из раздела «Export row» в `interfaces.md`. Строки есть только у файлов с готовым таймлайном (лица и голос). У остальных сеансов файл содержит только заголовок. |
| `GET /api/streams` | `api.listStreams` | `state/appData.ts`: сетка потоков, боковая панель, экран потока, «Настройки › Камеры» | 8 камер: 6 в состоянии `running`, одна `connecting`, одна `error`. |
| `POST /api/streams` | `api.createStream` | `streams/AddStreamDialog.tsx` | Проверяет, что название не пустое, а адрес начинается с `rtsp://`. Иначе ошибка «Укажите название и адрес вида rtsp://…». Новая камера сразу получает `connecting`, а через 2,5 с — `running` и сессию `rtsp`. |
| `PATCH /api/streams/{id}` | `api.updateStream` | `settings/CamerasTab.tsx` | Объединяет поля и `settings`. Если `enabled: false`, камера переходит в `stopped`. При повторном включении — снова `running`. |
| `DELETE /api/streams/{id}` | `api.deleteStream` | «Настройки › Камеры» | Удаляет камеру и рассылает `stream_status: stopped`. |
| `POST /api/streams/{id}/reconnect` | `api.reconnectStream` | `streams/StreamDetail.tsx` | Переводит камеру в `reconnecting`, через 3 с — в `error` с текстом «Источник не отвечает (заглушка)». Если анализ камеры выключен, возвращает ошибку «Анализ этой камеры выключен». |
| `POST /api/streams/test` | `api.testStream` | «Добавить поток» › «Проверить» | Адрес не `rtsp://`: `ok: false`. Адрес содержит `unreachable` или `0.0.0.0`: «Нет ответа от камеры». Остальные адреса: `ok: true`, 1920×1080, со звуком. |
| `GET /api/streams/{id}/log?interval_s=&limit=` | `api.fetchStreamLog` | журнал на экране потока | До 12 случайных интервалов. Для камеры не в `running` — пустой список. |
| `GET /api/system` | `api.fetchSystem` | экраны не вызывают (нагрузка приходит через `/ws/streams`) | Случайные CPU, RAM, GPU и VRAM около реальных значений для RTX 3050. |
| `GET /api/events?kind=&state=&stream_id=&session_id=&from_ms=&to_ms=&limit=&before_id=` | `api.listEvents` | колокольчик (`appData`), «История › События», результат анализа файла | Все фильтры и постраничная выдача через `before_id`. В журнале 6 стартовых событий (одно новое — инцидент на «Ресепшн»). Новые события создают симуляция камер, анализ файлов и сеансы веб-камеры. |
| `POST /api/events/{id}/ack` | `api.ackEvent` (через `appData.ack`) | колокольчик, баннер на экране потока, «История › События» | Записывает `confirmed` или `false_alarm` и рассылает событие в `/ws/streams`. Для позитивного события — «Подтверждать можно только негативные события». Для неизвестного id — «Событие не найдено». |
| `GET /api/events/export?...&format=` | `api.exportEvents` | «История › События» › «Экспорт» | Ссылка `data:` с отфильтрованным журналом без постраничного деления. Имя файла `events.csv` или `events.json`. |
| `GET /api/settings` | `api.fetchSettings` | `settings/SettingsPage.tsx`, интервал журнала на экране потока | Настройки в памяти, по умолчанию `DEFAULT_SETTINGS`. |
| `PUT /api/settings` | `api.saveSettings` | «Настройки › События» | Сохраняет настройки в памяти. Пороги и длительности сразу влияют на правило событий в симуляции. |
| `GET /api/sessions?kind=file` | `api.listFileSessions` | `analyze/AnalyzePage.tsx` (опрос 1 с или 10 с), имена файлов в «Событиях» | 5 демо-файлов: готовый, в обработке, в очереди, готовый без звука, с ошибкой. Затем загруженные файлы. |
| `GET /api/sessions/{id}` | `api.fetchFileSession` | экраны не вызывают (в настоящем клиенте его вызывает `uploadFile`) | Файл по id или «Сессия не найдена». |
| `POST /api/files` (multipart, XHR) | `api.uploadFile` | «Анализ видео» › «Выбрать файлы» или перетаскивание | Файл никуда не отправляется. Прогресс 25, 50, 75 и 100 % с шагом 150 мс. Браузер читает длительность и разрешение ролика. Файл встаёт в очередь, обработка идёт 10 % в секунду, затем генерируется результат. |
| `GET /api/sessions/{id}/timeline` | `api.fetchTimeline` | результат анализа файла | Кадры с частотой 5 к/с (лица, рамки, решения) и голосовые окна раз в секунду. До окончания обработки — «Результат ещё не готов». |
| `GET /api/sessions/{id}/media` | `api.fileMediaUrl` | плеер в результате анализа | Загруженный файл: `blob:` URL локального файла, видео играет, рамки рисуются поверх. У демо-файлов видео нет: пустой `data:` URL и пометка `playback_unavailable`, поэтому плеер показывает «Браузер не может воспроизвести этот формат», а рамки и графики работают. |

## WebSocket

| Канал | Функция | Где используется | Что делает заглушка |
|---|---|---|---|
| `/ws/streams` | `api.connectStreams` | `state/appData.ts`: все экраны потоков, колокольчик, строка нагрузки | Сразу вызывает `onConnection({ type: "open", first: true })` и рассылает `stream_status` всех камер. Каждые 200 мс отправляет `stream_result` для каждой камеры в `running` (симуляция из `sim.ts`). Сообщение `event` отправляется при новом событии и при подтверждении. Сообщение `system` отправляется раз в секунду. Бинарные кадры: раз в секунду на каждую камеру рисуется синтетический JPEG на canvas (фон, силуэты в местах лиц, название камеры и время). Обрыв и переподключение не симулируются. |
| `/ws/live` | `openLiveSocket` (`src/api/stub/live.ts`) | `live/run.ts`, экран «Веб-камера» | Открывается через 100 мс. На `start` отвечает `session` и создаёт сеанс `live`. На каждый кадр (0x01) через 40–60 мс приходит `frame_result` с одним лицом, рамка строится по размеру JPEG из заголовка SOF. Аудио (0x02) включает блок `audio`: речь определяется по громкости (RMS > 600), окно действует 2 с. `fused` смешивает лицо и голос в пропорции 0,7 и 0,3, пока есть речь. Решения и события идут через то же правило, события попадают в журнал и колокольчик. `stop` и `close` завершают сеанс. |

## Что изменено относительно оригинала

- `src/api/index.ts` берёт всё из `./stub` вместо `./real` и `./streamsSocket`.
- `src/live/run.ts` создаёт `openLiveSocket()` вместо `new WebSocket(...)`. Поле `ws` имеет тип `LiveSocket`, то есть ту часть `WebSocket`, которую использует `LiveRun`.
- `vite.config.ts`: убран proxy `/api` и `/ws` на `localhost:8000`.
- `nginx.conf`: убраны `location /api/` и `/ws/`, `resolver` и `client_max_body_size`. Остались только раздача SPA и кэш `assets`.
- `src/sessions/SessionsView.test.tsx` ждёт ссылки экспорта `data:` вместо `/api/sessions/...`.
- Добавлены `src/api/stub/*`, `STUBS.md` и `.gitignore`.

## Ограничения

- Данные случайные. Правило событий повторяет `stack.md` и берёт пороги из настроек, но вероятности эмоций не связаны с изображением. На экране «Веб-камера» рамка не следует за лицом.
- Ошибки сервера (нет связи, 5xx, загрузка моделей) не симулируются. Чтобы проверить такое состояние, верните `fail("текст")` из нужной функции в `src/api/stub/index.ts`.
- `__resetStub()` возвращает заглушку в исходное состояние. Эта функция нужна только тестам.

## Как вернуть настоящий бэкенд

1. В `src/api/index.ts` верните импорт из `./real` и `connectStreamsSocket` из `./streamsSocket`. Исходный вариант лежит в оригинальном репозитории, файл `frontend/src/api/index.ts`.
2. В `src/live/run.ts` верните создание сокета:
   ```ts
   const proto = location.protocol === "https:" ? "wss:" : "ws:";
   this.ws = new WebSocket(`${proto}//${location.host}/ws/live`);
   ```
   и тип поля `private ws: WebSocket`.
3. Верните proxy в `vite.config.ts` и `location /api/`, `/ws/` в `nginx.conf` из оригинала.
